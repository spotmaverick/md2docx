## 1. 概述

### 1.1 产品定位

面向个人与办公场景的**离线桌面工具**：把 Markdown 文档批量转换为可交付的 Word / WPS / 纯文本文件。
单文件 EXE 分发，双击即用，不安装、不联网、不依赖任何外部运行时。

### 1.2 本轮规格的核心变化

产品最初的形态是 `pywebview + WebView2 + 内置 HTTP 服务 + HTML/CSS/JS 前端`。
该方案在部分环境出现兼容性问题，根因是它把运行时可用性押在了外部组件上：

- 依赖系统安装 Edge WebView2 Runtime，缺失则界面无法启动；
- 依赖 `pythonnet` / `clr_loader`，受 .NET 运行环境与位数影响；
- 需要拉起本地 HTTP 端口，受防火墙、端口占用、安全软件干扰；
- 浏览器安全模型限制拖放文件的磁盘路径获取，导致「与源文件相同」等需求要靠
  `/api/locate` 枚举资源管理器窗口等间接手段实现，脆弱且难以稳定。

**因此确立 v1.0 的架构基线：改用纯本地的原生 Windows 桌面方案，彻底移除 Web 技术栈。**

#### v1.5 的变化：界面国际化 + 统一圆角

v1.5 是**纯界面层**的改动，不触碰解析、渲染与排版链路：

- **中英双语**：默认按操作系统界面语言自动判定（主语言为中文 → 中文界面，**其余一律英文**），
  用户可在标题栏右上角手动切换三档并把选择记住。所有可见文案收敛到 `i18n.STRINGS`，
  切换语言时**就地刷新、不重建窗口**。
- **统一圆角**：全部 6 个按钮改为 Canvas 自绘圆角（Tk 原生按钮没有圆角能力，
  自绘是维持"零第三方依赖"前提下的唯一路径）。
- **第 3 步控件组居中**：主按钮 + 打开输出文件夹 + 进度条 + 进度文字作为整体水平居中。

关键设计取舍：**文案与逻辑彻底解耦**。i18n 改造暴露出结果表曾用 `endswith("成功")`
判断转换成败——这类"逻辑依赖文案"的耦合在单语言下完全隐形，切换语言才会暴露，
故提炼为硬约束 FR-10.12，并由 `tools/check_i18n.py` 的语言判定用例与双语界面快照双重把关。

### 1.3 范围

| 范围内 | 范围外 |
| --- | --- |
| Markdown → docx / doc / wps / txt 的本地转换 | 在线转换服务、账号体系、云端同步 |
| 原生桌面 GUI 与命令行两种使用方式 | 移动端 / macOS / Linux 适配 |
| 本机 Word / WPS 的可选调用（高质量模式） | 内嵌自研 Office 排版引擎 |
| 单文件 EXE 打包与分发 | 自动更新、安装程序 |
| 界面语言：中文 / 英文两种，自动判定 + 手动切换 | 第三种及更多语言；界面语言影响**输出文档**的语言 |

### 1.4 术语

| 术语 | 含义 |
| --- | --- |
| 原生模式 / 高质量模式 | 调用本机 Word 或 WPS 的 COM 接口另存为二进制 .doc / .wps |
| RTF 兼容格式 | 内置 RTF 渲染器产出的载体文件，Word / WPS / LibreOffice 均可直接打开 |
| 版心 | 页面去掉左右上下页边距后的可排版区域（A4 + 2.5cm 边距时为 16cm × 24.7cm） |
| 折叠区 | 默认收起、点击标题栏展开的次级选项区块 |
| 语言档位 | 语言下拉框的三个取值：`自动`（跟随系统）/ `中文` / `English`。**「自动」本身也是一个显式档位**，与两个强制档位一样会被持久化 |
| 圆角按钮 | `gui.RoundButton`——用 Canvas 平滑多边形自绘的按钮。Tk 原生 `tk.Button` 没有圆角能力，自绘是唯一的零依赖实现路径 |

### 3.5 FR-5 高质量模式（可选调用本机 Office）

| 编号 | 需求 | 状态 |
| --- | --- | --- |
| FR-5.1 | 开关位于折叠区标题栏右侧，启用后 `.doc` / `.wps` 走本机 Word / WPS 另存为原生二进制格式 | 已实现 |

| FR-5.4 | 本机无 Word / WPS 时开关置灰并强制关闭，`.doc` / `.wps` 回退内置 RTF，功能不受影响 | 已实现 |
| FR-5.5 | 原生转换失败（超时 / 异常）时自动降级为 RTF 并在结果行给出告警，不阻断其它格式 | 已实现 |
| FR-5.6 | 转换流程：先生成临时 `.docx` → 由 Office `SaveAs2` 另存为目标格式 → 清理临时文件 | 已实现 |
| FR-5.7 | COM 调用超时上限 120 秒，超时判定为失败 | 已实现 |
| FR-5.8 | 界面顶部徽标显示检测结果：「● Word / WPS 已就绪」或「○ 未检测到 Word / WPS」 | 已实现 |

> **关键约束（FR-5.2 的依据）**：WPS 安装时会劫持标准 `Word.Application` ProgID 及 CLSID
> `{000209FF-…}`，把 `LocalServer32` 指向自身 `wps.exe`。仅检测 ProgID 存在与否必然把 WPS
> 误报成 Word。正确做法是逐级解析 `HKCR\<ProgID>\CLSID` → `HKLM\SOFTWARE\Classes\CLSID\{id}\LocalServer32`
> 的实际可执行文件路径，按 `winword.exe` / 路径含 `kingsoft`·`wps`·`wps.exe` 归属分类。
> 本机实测结论：`word=False`、`wps=True`。

| FR-10.11 | 中英两份词条键集必须完全一致；导入 i18n 模块时自检，不一致立即抛错（避免线上缺词条） | 已实现（硬约束） |
| FR-10.12 | 任何逻辑判断**不得依赖界面文案**（例如用 `endswith("成功")` 判断转换成功）——文案会随语言变化，属隐性耦合 | 已实现 |
| FR-10.13 | 纯 ASCII 的技术名词（`python-docx`、`RTF`、`docx` 等）两种语言下保持原样，不做翻译 | 已实现 |
| FR-10.14 | **输出文档正文的语言由源 Markdown 决定，不随界面语言变化**（如 `.txt` 中图片退化为 `[图片：alt]` 占位）。此为显式豁免项，见待办 G-07 | 已实现 |
| FR-10.15 | 配置读写失败必须静默降级（回落到系统语言与默认值），不得影响启动 | 已实现 |

> **为什么按 LANGID 主语言字段判定，而不是按国家/地区**
>
> 需求的原文是"根据操作系统语言配置设置"+"中国以外的地区一律用英文"。操作系统暴露的是
> **语言**（LANGID / LCID），不是地理位置；取主语言字段既覆盖了 `zh-CN`/`zh-TW`/`zh-HK`/
> `zh-MO`/`zh-SG` 全部中文变体，又天然把日韩德法等语种划到英文侧，与需求字面完全对应。
> 副作用是"位于境外但使用中文系统"的用户会得到中文界面——这与"按操作系统语言"一致，
> 且用户可手动切换（FR-10.5），故不作为缺陷。

## 6. 技术方案与模块结构

### 6.1 技术选型

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 界面 | **Tkinter / ttk** | Python 标准库，操作系统原生控件，**非 Web 技术** |
| Markdown 解析 | markdown-it-py + mdit-py-plugins | CommonMark 兼容，覆盖表格 / 围栏代码 / 任意缩进嵌套列表 |
| HTML 解析 | BeautifulSoup | 承接 markdown-it 的 HTML 输出，构建语义模型 |
| DOCX 生成 | python-docx | 原生 OOXML，不依赖 Office |
| DOC / WPS 生成 | 自研 RTF 渲染器 | 纯文本格式，Word / WPS / LibreOffice 均可原生打开 |
| 原生 Office 调用 | pywin32（win32com） | 可选，仅「高质量模式」使用 |
| 界面语言 | 自研 `src/i18n.py`（词条表 + 判定 + 运行时切换） | 不引入 gettext / Babel：本产品的语言集是封闭的两种，自研可把"缺词条""硬编码"变成导入期即暴露的硬错误 |
| 语言配置持久化 | `src/settings.py` → `%APPDATA%\Md2docs\settings.json` | 原子写（`.tmp` + `os.replace`），读写失败静默降级，不干扰启动 |
| 圆角按钮 | Canvas 平滑多边形自绘（`gui.RoundButton`） | Tk 原生按钮无圆角能力；自绘维持零第三方依赖的既定约束 |
| 拖放 | Win32 `WM_DROPFILES` | 通过 ctypes 直接调用，零第三方依赖。**硬约束 UI-17**：窗口过程回调只入队、不碰 Tk，否则进程会因 GIL 状态被破坏而直接退出（V-11） |
| 打包 | PyInstaller 6.x（onefile + windowed） | Tcl/Tk 运行时分发时内嵌 |

### 6.3 数据流

```
.md 文件
  → read_text（多编码探测）
  → mdparse.parse_markdown（markdown-it → HTML → BeautifulSoup → [Block]）
  → convert.convert_file 按格式分派
      ├─ docx_writer.write_docx   → .docx
      ├─ rtf_writer.write_rtf     → .doc / .wps（默认）
      ├─ com_helper.save_as       → .doc / .wps（高质量模式，先经 .docx）
      └─ txt_writer.write_txt     → .txt
  → [Result]（逐条结果：目标路径 / 大小 / 引擎 / 告警）
```

### 6.4 中间语义模型

- `Run`：行内片段，字段 `text / bold / italic / strike / code / sup / sub / link / image / brk`
- `Block`：块级节点，`kind` 取值 `heading / para / code / quote / list / table / hr / image`，
  辅以 `level / runs / text / lang / ordered / start / items / rows / header / src / alt`

所有渲染器只消费该模型，互不感知格式细节——新增输出格式只需新增一个 writer。

### 8.1 验证手段

| 手段 | 载体 | 覆盖内容 |
| --- | --- | --- |
| 结构自检 | `tools/check_output.py` | DOCX 必需元素（标题样式、超链接、底纹、图片 InlineShapes 且宽高 ≤ 版心）；RTF 必需指令、`\uN` 单字节回退配对、`\pict` 带 png/jpeg blip 且 `picwgoal`/`pichgoal` ≤ 版心 |

| 国际化回归 | `python tools/check_i18n.py [-v]` | ① 词条自洽：中英键集一致、被引用的键都存在、无闲置键；② 硬编码扫描：ast 解析 `src/*.py` 的字符串常量，报告未走 i18n 的中文文案（输出文档正文显式豁免）；③ **语言判定规则**：把 13 条 LANGID 打桩灌进 `_detect_windows()`，逐条核对"中文 → zh、其余一律 en"，并校验 `显式档位 > MD2DOCS_LANG > 系统探测` 的优先级；④ 双语界面快照：切 en 后采集全部可见文案，不允许残留中文、不允许把词条键当文案显示。**③ 不可省**——本机是中文系统，不灌 LANGID 就永远看不到判定分支，规则写错也测不出来 |
| 版式回归 | `python tools/check_ui_layout.py` | 断言 6 个按钮都确实是圆角（Canvas 平滑多边形且点数 ≥ 12，退回 `tk.Button` 会立刻失败）；断言第 3 步控件组在 zh / en 下均水平居中（左右余量偏差 ≤ 1px）。同样要求**已映射**窗口 |
| 界面回归（源码） | `python tools/check_gui_width.py` | 在**已映射**窗口下用真实点击事件反复点击格式卡片并开合折叠区，断言窗口宽度恒定（UI-16 / V-10）。注意窗口未映射时缺陷不显现，必须在映射态运行 |
| 界面回归（产物） | `python tools/check_exe_gui.py dist/Md2docs.exe` | 对打包后的 EXE 投递**真实鼠标点击**（PostMessage 到子窗口对 Tk 无效，已实测排除），断言宽度恒定；点击是否真正生效以**客户区网格取色指纹**的变化为准。运行前先校验目标点上是否为本窗口，被遮挡时判定为"不可判定"而非给出假通过。实测本机遮挡物是 **Windows 聚焦（Spotlight）全屏层**（类名 `Windows.UI.Core.CoreWindow`、标题随图片变化、rect 覆盖 1920×1080），它**不是**标准锁屏（`LockScreenBackstopFrame`），仅凭类名判断容易误判为"并未遮挡" |
| 拖放回归 | `python tools/check_dnd.py [--exe] [--argv]` | 按 shell 的 `HDROP` 内存布局构造句柄并投递**真实 `WM_DROPFILES` 消息**（即资源管理器拖放时发出的同一条消息）。常规用例：单文件 / 多文件 / 重复去重 / 连续拖放 5 次；**边界用例**：目录展开、不存在的路径、非 Markdown 文件、大写扩展名、空 HDROP、非法 HDROP 句柄（`0xDEADBEEF`）、一次拖入 150 个文件。源码模式与打包 EXE 两种载体；`--argv` 覆盖「把文件拖到 EXE 图标上」的命令行入口。该探针不依赖真实鼠标输入，桌面被遮挡时同样有效（V-11） |

| 转换回归 | `sample/示例文档.md`、`tests/stress.md`、`tests/imgs_case.md` | 语法覆盖、极端排版、图片各形态（超宽 / 超高 / 小图 / 行内 / data URI / 缺失文件） |
| 阅读器实测 | WPS COM 打开产物 | 以真实阅读器视角核对图片数量、显示尺寸与段落对齐（比解包 XML 更接近用户实际所见） |
| 多缩放验证 | 125% / 150% DPI | 布局不溢出、页脚不被截断 |

> **为什么拖放验证用消息投递，而不是鼠标模拟真实拖拽**
>
> 本窗口以 `DragAcceptFiles` 注册的是 **Shell 拖放**。真实拖拽（无论来自资源管理器还是 OLE
> `DoDragDrop`）最终都由 Shell 转成 `WM_DROPFILES` 投递到本窗口——探针投递的正是同一条消息、
> 进入同一段窗口过程。中间的 OLE 拖放源、鼠标捕获、Shell 解析均在 Md2docs 进程之外，
> 不属于被测代码，也不可能导致本程序崩溃。
>
> 浏览器自动化工具（Playwright / agent-browser 等）无法参与此类验证：它们只能驱动自带的
> 浏览器实例，经 CDP 在页面 DOM 上合成事件，**看不见也碰不到原生 Win32 窗口**——这是射程
> 问题而非能力问题。同理，任何依赖真实鼠标输入的方案（`mouse_event` / `SendInput`）在桌面
> 被全屏窗口遮挡或锁屏时一律失效，而消息投递不受影响。
>
> 因此当外部输入通道受限时，验证重心应放在**窗口过程与消费端的边界**上。
