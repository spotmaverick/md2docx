## 1. 概述

### 1.1 产品定位

面向个人与办公场景的**离线桌面工具**：把 Markdown 文档批量转换为可交付的 Word / WPS / 纯文本文件。
单文件 EXE 分发，双击即用，不安装、不联网、不依赖任何外部运行时。

### 1.2 本轮规格的核心变化

产品最初的形态是 `pywebview + WebView2 + 内置 HTTP 服务 + HTML/CSS/JS 前端`。
该方案在部分环境出现兼容性问题，根因是它把运行时可用性押在了外部组件上：

- 依赖系统安装 Edge WebView2 Runtime，缺失则界面无法启动；
- 依赖 `pythonnet` / `clr_loader`，受 .NET 运行环境与位数影响；
- 需要拉起本地 HTTP 端口，受防火墙、端口占用、安全软件干扰；
- 浏览器安全模型限制拖放文件的磁盘路径获取，导致「与源文件相同」等需求要靠
  `/api/locate` 枚举资源管理器窗口等间接手段实现，脆弱且难以稳定。

**因此确立 v1.0 的架构基线：改用纯本地的原生 Windows 桌面方案，彻底移除 Web 技术栈。**

#### v1.5 的变化：界面国际化 + 统一圆角

v1.5 是**纯界面层**的改动，不触碰解析、渲染与排版链路：

- **中英双语**：默认按操作系统界面语言自动判定（主语言为中文 → 中文界面，**其余一律英文**），
  用户可在标题栏右上角手动切换三档并把选择记住。所有可见文案收敛到 `i18n.STRINGS`，
  切换语言时**就地刷新、不重建窗口**。
- **统一圆角**：全部 6 个按钮改为 Canvas 自绘圆角（Tk 原生按钮没有圆角能力，
  自绘是维持"零第三方依赖"前提下的唯一路径）。
- **第 3 步控件组居中**：主按钮 + 打开输出文件夹 + 进度条 + 进度文字作为整体水平居中。

关键设计取舍：**文案与逻辑彻底解耦**。i18n 改造暴露出结果表曾用 `endswith("成功")`
判断转换成败——这类"逻辑依赖文案"的耦合在单语言下完全隐形，切换语言才会暴露，
故提炼为硬约束 FR-10.12，并由 `tools/check_i18n.py` 的语言判定用例与双语界面快照双重把关。

#### v1.6 的变化：修掉"一个符号把程序带崩"

v1.5 交付后，从用户实际环境反馈回来一个故障：**跑 `--selftest` 弹出「Md2docs 启动失败」**。
根因不在转换链路，而在一个字符：

- 结果表状态列写的是 `✓ 成功` / `✕ 失败`（U+2713 / U+2715）。这两个字符 **GBK 编码不了**，
  而 `--selftest` 会把结果表逐行打到控制台 → `UnicodeEncodeError` → 冒到 `main` 兜底
  → 模态框。用户看到"程序起不来"，真实原因是"一个符号打不出来"。
- 该字符同时是"微软雅黑没有字形"的字符；本机 Tk 靠系统字体回退把它画了出来（已实测确认，
  见 FR-10.16 的说明），所以界面侧没有可见异常——**但不该把正确性押在回退上**。
- 另一半问题是"放大器"：`--cli` / `--selftest` / `--diag` 出错时同样弹模态框，
  把自动化入口变成了会挂死人机交互的入口。

处置：状态列改用 GB2312 符号区的 `√` / `×`（FR-10.16）；标准输出置为有损模式
（FR-10.17）；自动化入口改为只写日志与控制台并返回可信退出码（FR-9.11 / FR-9.12）；
顺带修掉 onefile 退出时强杀引导父进程把**退出码抹成 0**、以及未冲缓冲导致重定向输出
尾部丢失两个问题；并新增逐字符核验的工具 `tools/check_font_glyphs.py`，
把"用字约束"从口头约定变成断言。

#### v1.7 的变化：退出时不再冒黑框（顺带捞出一起静默失败）

用户反馈：**退出程序时会闪出一个黑框**。根因在退出收尾的后台清理子进程：

- 它以 `DETACHED_PROCESS(0x8) | CREATE_NO_WINDOW(0x08000000)` 创建。MSDN 在
  `CREATE_NO_WINDOW` 条目里明写它与 `DETACHED_PROCESS` 同用时**被忽略**——
  于是"不要窗口"这条指令被系统丢掉，`cmd.exe` 在无控制台可继承的情况下自行
  分配一个新控制台。用户于是看到：关掉程序后凭空冒出黑框，还要干等
  `ping -n 4` 跑满约 3 秒才消失。
- 查这条时带出了更麻烦的一个：该子进程用 **list 形式**传给 `subprocess`，
  内层引号被 `list2cmdline` 转义成 `\"`，而 cmd 不认反斜杠转义（它用 `""`
  表示字面引号）→ `rd` 收到 `\"D:\...\"` 这样的非法路径 → 报"文件名、目录名
  或卷标语法不正确"后**静默失败**。也就是说 **`_MEI` 解包目录从来就没被删掉过**，
  一直在往 `%TEMP%` 里堆。它之所以一直没被发现，是因为子进程的退出码与输出
  都被丢掉了，"看起来做了"和"真的做了"没有任何区别。

处置：只保留 `CREATE_NO_WINDOW` 并补 `SW_HIDE`（NFR-08）；改用**原始命令行
字符串**配合 cmd 的 `""path""` 写法（实测 rc=0 且目录确实消失）；确立 NFR-09
——后台子进程不得静默失败，其**效果**必须有回归断言（新增
`tools/check_no_console_window.py`，自带正反对照与真机端到端）。

#### v1.8 的变化：按钮真正居中；补齐对外文档

用户反馈：**「开始转换」按钮仍然靠左对齐**。版式回归当时是通过的，但它量错了对象：

- 回归断言的是"第 3 步**控件组**在 `bar` 里居中"——而控件组确实居中（左右余量各 128px，
  偏差 0px）。问题在于**按钮是控件组里最左边的元素**，组居中不等于按钮居中，
  视觉上按钮依旧贴在左侧（V-17）。
- 更隐蔽的一层：进度文字用了 `width=16` 的定宽占位，为空时它仍占着约 160px。
  这块"看不见的宽度"把整组的**可见内容**又往左推了约 80px。

改为：让「开始转换」在**整行**里居中 `pack`，次级控件（「打开输出文件夹」与进度区）
用 `place` 钉在行的左右两端。`place` 不参与 `pack` 布局，所以既不影响按钮居中，
也不增加高度。回归断言随之改为**直接量按钮自身的中心**（而不是父容器的居中状态），
并追加"次级控件不得与按钮重叠"。

同时记录一处**中途踩到又修掉的回归**：最初的做法是"按钮独占一行 + 次级控件另起一行"。
它确实能居中，默认态高度也只从 911 涨到 952（看着还够），但把三个折叠区全展开后
`main_req` 冲到 971(zh) / 992(en)，而两张表早已被压到 2 行下限、再也腾不出空间
——**内容直接顶破可用高度（avail 964）**。这暴露出一条更一般的教训：
**高度只测默认态是没意义的**，折叠区展开才是峰值。为此新增
`tools/check_fold_fit.py`，把"默认态与折叠全展开态都必须放得下"变成常驻断言。

对外文档同步补齐：新增完整 `README.md`（含界面截图、命令行参数表、构建步骤、
回归工具清单、常见问题）、`requirements.txt` 与 `requirements-dev.txt`
（此前项目没有任何依赖清单，README 里的安装步骤无法照做）。

#### v1.9 的变化：语言入口改用地球图标

用户提出：**【语言】选项的标题不能用文字，改为地球标识** —— 否则读不懂当前界面
语言的用户找不到改语言的入口。

这条提得准。原来的标识是"语言 / Language"，而这段文字本身也是由**当前界面语言**
写成的：用户要找的正是改语言的地方，却先被一段他读不懂的文字挡住，入口形同不存在
（V-19）。判定规则本身也会造成这种不一致（中文系统→中文、其余→英文），用户手切
档位同样会。

改为 `gui.GlobeIcon` 自绘矢量地球（外圈 + 中央经线 + 赤道），并**刻意不用任何字符**：
`🌐`(U+1F310) 既不在 GBK 内、也不保证字形存在（`tools/check_font_glyphs.py` 会拦下
放进词条的字形写法），而画椭圆不经过字体，天然免疫字形与编码风险，也不需要图片资源。
图标可点——点它就展开列表（只读下拉框本身就是"一个大按钮"，实测在控件任意位置投递
一次点击都会展开，所以不必依赖 `ttk::combobox::*` 内部命令）。列表里每种语言一律用
本名书写（`中文` / `English`），谁都能认出自己那一项；`lang.label` 词条随之删除。

新增常驻回归 `tools/check_lang_entry.py`：断言标识是矢量绘制且**零 text 图元**、
入口子树里没有任何静态文字控件，并做**真机点击链路**（点图标 → 展开 → 选中 →
语言与窗口标题真的切换，两轮覆盖正反方向）；**自带正控**（两个坏样本必须被检出，
否则判探针失效），运行期拦截 `settings.put` 以免污染主人的真实配置。

写这个工具时又踩到一次同类缺陷（V-20）：**失败提示里写了字面的 `🌐`**，于是
"缺陷被成功检出、工具却在打印失败原因时自己抛 `UnicodeEncodeError`"——报错信息
本身打不出来。据此新增 §8.4：面向控制台的输出一律有损，**错误路径尤其**。

### 1.3 范围

| 范围内 | 范围外 |
| --- | --- |
| Markdown → docx / doc / wps / txt 的本地转换 | 在线转换服务、账号体系、云端同步 |
| 原生桌面 GUI 与命令行两种使用方式 | 移动端 / macOS / Linux 适配 |
| 本机 Word / WPS 的可选调用（高质量模式） | 内嵌自研 Office 排版引擎 |
| 单文件 EXE 打包与分发 | 自动更新、安装程序 |
| 界面语言：中文 / 英文两种，自动判定 + 手动切换 | 第三种及更多语言；界面语言影响**输出文档**的语言 |

### 1.4 术语

| 术语 | 含义 |
| --- | --- |
| 原生模式 / 高质量模式 | 调用本机 Word 或 WPS 的 COM 接口另存为二进制 .doc / .wps |
| RTF 兼容格式 | 内置 RTF 渲染器产出的载体文件，Word / WPS / LibreOffice 均可直接打开 |
| 版心 | 页面去掉左右上下页边距后的可排版区域（A4 + 2.5cm 边距时为 16cm × 24.7cm） |
| 折叠区 | 默认收起、点击标题栏展开的次级选项区块 |
| 语言档位 | 语言下拉框的三个取值：`自动`（跟随系统）/ `中文` / `English`。**「自动」本身也是一个显式档位**，与两个强制档位一样会被持久化 |
| 圆角按钮 | `gui.RoundButton`——用 Canvas 平滑多边形自绘的按钮。Tk 原生 `tk.Button` 没有圆角能力，自绘是唯一的零依赖实现路径 |

> **为什么 FR-10.16 是硬约束而不是"注意一下细节"**
>
> **已核实的一条**：GBK 编不出来的字符只要进了 `print`，就会把程序带进
> "启动失败"模态框——`--selftest` 会把结果表逐行打到标准输出，`✓` 一出手就抛
> `UnicodeEncodeError: 'gbk' codec can't encode character '\u2713'`，异常冒到 `main`
> 的兜底分支。用户看到的是"程序起不来"，真实原因却是"有个符号打不出来"（V-14）。
>
> **"缺字形"这一条性质更微妙，写清楚以免误判**：微软雅黑确实没有 U+2713 / U+2715
> 的字形（GDI `GetGlyphIndicesW` 返回 0xFFFF），但**本机实测 Tk 仍把 `✓` 画出来了**
> ——用 PrintWindow 逐像素比对，`✓` 的位图与"确定缺字形"的私用区字符 U+E000
> 的豆腐块位图**明显不同**，说明是系统做了字体回退。也就是说：界面侧当时并没有
> 观察到方框，靠的是回退这个**不可依赖的运气**。
>
> 结论不变，理由更准确：用字约束的目的不是"修一个看得见的方框"，而是**把这个字符
> 从"依赖回退"和"依赖控制台编码"两个不确定性里彻底摘出去**——GB2312 符号区的字符
> 两个条件同时满足，且 `tools/check_font_glyphs.py` 能把它变成机械断言。

> **为什么按 LANGID 主语言字段判定，而不是按国家/地区**
>
> 需求的原文是"根据操作系统语言配置设置"+"中国以外的地区一律用英文"。操作系统暴露的是
> **语言**（LANGID / LCID），不是地理位置；取主语言字段既覆盖了 `zh-CN`/`zh-TW`/`zh-HK`/
> `zh-MO`/`zh-SG` 全部中文变体，又天然把日韩德法等语种划到英文侧，与需求字面完全对应。
> 副作用是"位于境外但使用中文系统"的用户会得到中文界面——这与"按操作系统语言"一致，
> 且用户可手动切换（FR-10.5），故不作为缺陷。

## 6. 技术方案与模块结构

### 6.1 技术选型

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 界面 | **Tkinter / ttk** | Python 标准库，操作系统原生控件，**非 Web 技术** |
| Markdown 解析 | markdown-it-py + mdit-py-plugins | CommonMark 兼容，覆盖表格 / 围栏代码 / 任意缩进嵌套列表 |
| HTML 解析 | BeautifulSoup | 承接 markdown-it 的 HTML 输出，构建语义模型 |
| DOCX 生成 | python-docx | 原生 OOXML，不依赖 Office |
| DOC / WPS 生成 | 自研 RTF 渲染器 | 纯文本格式，Word / WPS / LibreOffice 均可原生打开 |
| 原生 Office 调用 | pywin32（win32com） | 可选，仅「高质量模式」使用 |
| 界面语言 | 自研 `src/i18n.py`（词条表 + 判定 + 运行时切换） | 不引入 gettext / Babel：本产品的语言集是封闭的两种，自研可把"缺词条""硬编码"变成导入期即暴露的硬错误 |
| 语言配置持久化 | `src/settings.py` → `%APPDATA%\Md2docs\settings.json` | 原子写（`.tmp` + `os.replace`），读写失败静默降级，不干扰启动 |
| 圆角按钮 | Canvas 平滑多边形自绘（`gui.RoundButton`） | Tk 原生按钮无圆角能力；自绘维持零第三方依赖的既定约束 |
| 拖放 | Win32 `WM_DROPFILES` | 通过 ctypes 直接调用，零第三方依赖。**硬约束 UI-17**：窗口过程回调只入队、不碰 Tk，否则进程会因 GIL 状态被破坏而直接退出（V-11） |
| 打包 | PyInstaller 6.x（onefile + windowed） | Tcl/Tk 运行时分发时内嵌 |

### 6.3 数据流

```
.md 文件
  → read_text（多编码探测）
  → mdparse.parse_markdown（markdown-it → HTML → BeautifulSoup → [Block]）
  → convert.convert_file 按格式分派
      ├─ docx_writer.write_docx   → .docx
      ├─ rtf_writer.write_rtf     → .doc / .wps（默认）
      ├─ com_helper.save_as       → .doc / .wps（高质量模式，先经 .docx）
      └─ txt_writer.write_txt     → .txt
  → [Result]（逐条结果：目标路径 / 大小 / 引擎 / 告警）
```

### 6.4 中间语义模型

- `Run`：行内片段，字段 `text / bold / italic / strike / code / sup / sub / link / image / brk`
- `Block`：块级节点，`kind` 取值 `heading / para / code / quote / list / table / hr / image`，
  辅以 `level / runs / text / lang / ordered / start / items / rows / header / src / alt`

所有渲染器只消费该模型，互不感知格式细节——新增输出格式只需新增一个 writer。

## 8. 验证与验收

### 8.1 验证手段

| 手段 | 载体 | 覆盖内容 |
| --- | --- | --- |
| 结构自检 | `tools/check_output.py <输出目录> <文件名主干>` | DOCX 必需元素（标题样式、超链接、底纹、图片 InlineShapes 且宽高 ≤ 版心）；RTF 必需指令、`\uN` 单字节回退配对、`\pict` 带 png/jpeg blip 且 `picwgoal`/`pichgoal` ≤ 版心。<br>注意：DOCX 的"表格 / 超链接 / 底纹"三条断言是**对 `sample/示例文档.md` 这类含对应语法的固件**设计的；换用 `tests/imgs_case.md`（本身没有表格、超链接、代码块）时会报出这三条告警，属固件不匹配而非产物缺陷——判读时先看源 Markdown 有没有对应语法。 |
| 界面自检 | `python src/app.py --selftest [文件] [--out 目录]`（或 `dist/Md2docs.exe --selftest`） | 控件就绪、格式卡片数、默认值、**当前语言与档位**、**zh↔en 往返切换**、可选跑一次真实转换并断言 4 条结果全部成功 |
| 国际化回归 | `python tools/check_i18n.py [-v]` | ① 词条自洽：中英键集一致、被引用的键都存在、无闲置键；② 硬编码扫描：ast 解析 `src/*.py` 的字符串常量，报告未走 i18n 的中文文案（输出文档正文显式豁免）；③ **语言判定规则**：把 13 条 LANGID 打桩灌进 `_detect_windows()`，逐条核对"中文 → zh、其余一律 en"，并校验 `显式档位 > MD2DOCS_LANG > 系统探测` 的优先级；④ 双语界面快照：切 en 后采集全部可见文案，不允许残留中文、不允许把词条键当文案显示。**③ 不可省**——本机是中文系统，不灌 LANGID 就永远看不到判定分支，规则写错也测不出来 |
| 用字回归 | `python tools/check_font_glyphs.py [-v]` | 取 UI 实际字体的回退链（YaHei UI → YaHei → Segoe UI），用 GDI `GetGlyphIndicesW`(GGI_MARK_NONEXISTING_GLYPHS) 逐个核验词条里每个非 ASCII 字符**有字形**，并核验其**可被 GBK 编码**。任一不满足即失败。**必须用 `CreateFontIndirectW` + `LOGFONTW`**：误用 A 版接口传 UTF-16 字节串会让字体名失效，全部字符都"查不到字形"，得出与事实相反的结论 |
| 版式回归 | `python tools/check_ui_layout.py` | 断言 6 个按钮都确实是圆角（Canvas 平滑多边形且点数 ≥ 12，退回 `tk.Button` 会立刻失败）；断言**「开始转换」按钮自身的中心**在 zh / en 下均落在第 3 步面板正中（偏差 ≤ 1px），并断言次级控件与按钮不重叠。量的是按钮自身而非父容器——V-17 的教训。同样要求**已映射**窗口 |
| 高度余量回归 | `python tools/check_fold_fit.py` | 断言 `main_req ≤ avail` 且页脚完整可见，**默认态与三个折叠区全展开态都要过**。折叠区展开才是高度峰值：`_autosize` 会把两张表压到 2 行下限来腾空间，压到底仍不够就是顶破（V-18）。结果表到达 2 行下限时额外打印提醒（不算失败） |
| 语言入口回归 | `python tools/check_lang_entry.py` | 断言语言入口的标识是**自绘矢量地球**（Canvas 且 ≥3 个椭圆图元、**零 text 图元**——用字形画图标会重新引入字形缺失与编码风险），入口子树里**不存在任何静态文字控件**（不许把文字标签加回来），并做**真机点击链路**：在图标上投递真实点击 → 列表展开 → 点中某一行 → 界面语言与窗口标题确实切换；两轮覆盖 zh→English、en→中文，同时验证"英文界面下入口仍可辨认"。**自带正控**：先造两个坏样本（带文字的 `Label`、用 `create_text` 画的假图标），两段采集器都必须检出，否则判"探针失效"。运行期拦截 `settings.put`，**不改动主人的真实配置**。要求窗口已映射 |
| 界面回归（源码） | `python tools/check_gui_width.py` | 在**已映射**窗口下用真实点击事件反复点击格式卡片并开合折叠区，断言窗口宽度恒定（UI-16 / V-10）。注意窗口未映射时缺陷不显现，必须在映射态运行 |
| 界面回归（产物） | `python tools/check_exe_gui.py dist/Md2docs.exe` | 对打包后的 EXE 投递**真实鼠标点击**（PostMessage 到子窗口对 Tk 无效，已实测排除），断言宽度恒定；点击是否真正生效以**客户区网格取色指纹**的变化为准。运行前先校验目标点上是否为本窗口，被遮挡时判定为"不可判定"而非给出假通过。实测本机遮挡物是 **Windows 聚焦（Spotlight）全屏层**（类名 `Windows.UI.Core.CoreWindow`、标题随图片变化、rect 覆盖 1920×1080），它**不是**标准锁屏（`LockScreenBackstopFrame`），仅凭类名判断容易误判为"并未遮挡" |
| 拖放回归 | `python tools/check_dnd.py [--exe] [--argv]` | 按 shell 的 `HDROP` 内存布局构造句柄并投递**真实 `WM_DROPFILES` 消息**（即资源管理器拖放时发出的同一条消息）。常规用例：单文件 / 多文件 / 重复去重 / 连续拖放 5 次；**边界用例**：目录展开、不存在的路径、非 Markdown 文件、大写扩展名、空 HDROP、非法 HDROP 句柄（`0xDEADBEEF`）、一次拖入 150 个文件。源码模式与打包 EXE 两种载体；`--argv` 覆盖「把文件拖到 EXE 图标上」的命令行入口。该探针不依赖真实鼠标输入，桌面被遮挡时同样有效（V-11） |
| DPI 诊断 | `python src/app.py --diag` | 输出 tk 版本、缩放、屏幕 / 工作区尺寸、窗口与客户区矩形、内容需求尺寸、页脚是否完整可见 |
| 无窗口回归 | `python tools/check_no_console_window.py [--quick] [--exe [PATH]]` | 断言程序在启动、运行、**退出**全过程不产生计划外的可见窗口，且后台清理真的生效（NFR-08 / NFR-09）。做法：枚举顶层窗口里窗口类属于控制台的那些（`ConsoleWindowClass` / `CASCADIA_HOSTING_WINDOW_CLASS` / `PseudoConsoleWindow`），在 spawn 前后取差集。**自带正反对照**：正控故意用 buggy 组合（`DETACHED_PROCESS \| CREATE_NO_WINDOW`），**必须检出** ≥1 个新窗口，否则直接判"探针失效"而非判通过——看不见缺陷的探针给出的假通过比没有探针更危险（v1.6 的教训）。`--exe` 追加真机端到端，走两条出路：`--cli` 跑一次转换、以及启动图形界面后投递 `WM_CLOSE` 关窗（**即用户实际报的那条路径**）；两者都核对退出后 `%TEMP%` 下没有多出 `_MEI*` 残留 |
| 转换回归 | `sample/示例文档.md`、`tests/stress.md`、`tests/imgs_case.md` | 语法覆盖、极端排版、图片各形态（超宽 / 超高 / 小图 / 行内 / data URI / 缺失文件） |
| 阅读器实测 | WPS COM 打开产物 | 以真实阅读器视角核对图片数量、显示尺寸与段落对齐（比解包 XML 更接近用户实际所见） |
| 多缩放验证 | 125% / 150% DPI | 布局不溢出、页脚不被截断 |

> **为什么拖放验证用消息投递，而不是鼠标模拟真实拖拽**
>
> 本窗口以 `DragAcceptFiles` 注册的是 **Shell 拖放**。真实拖拽（无论来自资源管理器还是 OLE
> `DoDragDrop`）最终都由 Shell 转成 `WM_DROPFILES` 投递到本窗口——探针投递的正是同一条消息、
> 进入同一段窗口过程。中间的 OLE 拖放源、鼠标捕获、Shell 解析均在 Md2docs 进程之外，
> 不属于被测代码，也不可能导致本程序崩溃。
>
> 浏览器自动化工具（Playwright / agent-browser 等）无法参与此类验证：它们只能驱动自带的
> 浏览器实例，经 CDP 在页面 DOM 上合成事件，**看不见也碰不到原生 Win32 窗口**——这是射程
> 问题而非能力问题。同理，任何依赖真实鼠标输入的方案（`mouse_event` / `SendInput`）在桌面
> 被全屏窗口遮挡或锁屏时一律失效，而消息投递不受影响。
>
> 因此当外部输入通道受限时，验证重心应放在**窗口过程与消费端的边界**上。

### 8.3 验证环境的一个坑：环境变量会掩盖编码类缺陷

本机（以及本项目的开发 shell）默认带着：

```
PYTHONUTF8=1
PYTHONIOENCODING=utf-8
```

实测此时 `sys.flags.utf8_mode = 1`、`sys.stdout.encoding = utf-8`。**这意味着**：

* 开发期在 shell 里跑的每一次回归，标准输出都是 UTF-8——`✓` 写得出来、什么都不会报错；
* 用户的普通控制台没有这两个变量，`utf8_mode = 0`、stdout 是 `gbk`——同一个 `print` 当场抛异常。

于是出现最坏的一种验证假象：**在开发环境里全部绿灯，而真实环境里程序起不来**。
v1.5 的"全部回归通过"就是这么来的——功能、版式、宽度、拖放全都真的通过了，
唯独"控制台能不能打出这个字符"没被覆盖，因为开发环境的编码恰好是 UTF-8。

> 结论（已固化为回归纪律）：**凡是与编码、控制台、文件系统代码页、区域设置相关的验证，
> 必须在显式清空这些变量后的干净环境里跑**：
>
> ```bash
> unset PYTHONUTF8 PYTHONIOENCODING
> ```
>
> 判据不是"跑过了"，而是"在**目标环境**里跑过了"。打包产物的验证尤其如此——
> 实测这两个变量对 onefile 产物**不生效**（同一份环境，venv 的 python 是
> `utf8_mode=1`，`dist/Md2docs.exe` 仍按 GBK 输出并崩溃），所以打包产物的输出
> 行为必须单独确认，不能由源码态的表现推断。

### 8.4 同一个坑的另一半：**报错信息本身也可能打不出来**

写 `tools/check_lang_entry.py` 时亲历一次（V-20）：该工具的失败提示里直接写了
一个字面的 `🌐`。结果是最难看的一幕——**缺陷被成功检出，工具却在打印失败原因时
自己抛 `UnicodeEncodeError` 中断**，只报出一条就没了。中文控制台是 GBK，这个字符
打不出去。

这与 V-14 是**同一个缺陷换了个位置复发**：编码问题不会因为你已经修过它就不再出现，
它只是换到"没人觉得需要保护"的地方——错误路径。

> 结论（已固化为写法）：**面向控制台的输出一律设成有损**（`stream.reconfigure(
> errors="replace")`），**错误路径尤其**——因为错误路径恰是最需要把话说出来的地方。
> `app._make_output_safe()` 与各回归工具的 `_make_output_safe()` 是同一套做法；
> 提示文字里要提到某个字符时，用码位写法（`U+1F310`）而不是字面字符。
