## Md2docs v1.6：修掉「跑 --selftest 弹出启动失败」

### 故障与根因

主人反馈截图：`Md2docs 启动失败`，堆栈落在 `gui.py` 的 `_measure()`。经核对：

- 截图里那处是 **V-13**（`RoundButton` 误用 `self._w`/`self._h`），**已修复**。
  铁证在行号：旧代码 `_measure()` 在 365 行、报错的 `configure` 在 380 行，
  且第 380 行是 `super().configure(width=self._w, height=self._h)`；
  现在 `_measure()` 在 368 行、`configure` 在 383 行、用的是 `self._bw`/`self._bh`
  （中间正好多出 3 行警告注释）。截图必然取自修复前。
- 但顺着截图去查 `Documents\Md2docs\md2docs.log`，发现**当天确实有两次真实崩溃**
  （09:53:25、10:04:28），是**另一个**故障：`UnicodeEncodeError: 'gbk' codec
  can't encode character '\u2713'`，位置 `gui.py:1774 in selftest`。

根因链：

1. 结果表状态列写的是 `✓ 成功` / `✕ 失败`（U+2713 / U+2715）。**GBK 编码不了**这两个字符。
2. `--selftest` 会把结果表**逐行打到标准输出**（这行是我在 v1.5 加的——原来 selftest
   不跑转换，所以这条路径以前走不到）。
3. 用户的普通控制台是 GBK → `print` 抛异常 → 冒到 `main` 的 `except` → `_fatal`
   弹模态框。用户看到"程序起不来"，真实原因是"一个符号打不出来"。

### 为什么我上一轮的"全部回归通过"没拦住

我的开发 shell 带着 **`PYTHONUTF8=1` + `PYTHONIOENCODING=utf-8`**
（`sys.flags.utf8_mode=1`、`sys.stdout.encoding=utf-8`），输出永远 UTF-8，
这条路径**永远不报错**。用户控制台没有这两个变量 → `utf8_mode=0`、`stdout=gbk` → 必崩。

**这是最坏的一种验证假象：开发环境全绿，真实环境起不来。**
已把"编码 / 控制台 / 代码页 / 区域设置相关验证必须在 `unset PYTHONUTF8 PYTHONIOENCODING`
后的干净环境里跑"固化为纪律（写进规格 §8.3 与 MEMORY.md）。

另：**打包产物实测不认这两个环境变量**——同一份环境里 venv 的 python 是 `utf8_mode=1`，
`dist/Md2docs.exe` 仍按 GBK 输出并崩溃。所以打包产物的输出行为必须单独确认，
不能由源码态推断。

### 改动

- `src/i18n.py`：`res.state_ok` / `res.state_fail` 由 `✓` / `✕` 改为 GB2312 符号区的
  `√` / `×`（zh: `√ 成功` / `× 失败`，en: `√ Done` / `× Failed`）；模块文档补"文案用字约束"。
- `src/app.py`：
  - 新增 `_make_output_safe()`：把 stdout/stderr `reconfigure(errors="replace")`

  - `_fatal(msg, headless=False) -> int`：**模态框只在图形界面模式下弹**；
    `--cli` / `--selftest` / `--diag` 只写日志与控制台；统一返回失败码。

  - `_cleanup_frozen_exit(code)`：退出前 `flush()`；`TerminateProcess(h, code)`

## v1.7 退出时冒出 cmd 黑框（含一处藏了很久的静默失败）

### 问题
用户反馈：**退出程序时会闪出黑色 cmd 窗口**，要等一会儿才消失。

### 根因（两处，第二处更严重）

1. **窗口**：`_cleanup_frozen_exit` 里的后台清理子进程用
   `creationflags = DETACHED_PROCESS(0x00000008) | CREATE_NO_WINDOW(0x08000000)`。
   MSDN 在 `CREATE_NO_WINDOW` 条目里明写它与 `DETACHED_PROCESS` **同用时被忽略**。
   于是"不显示窗口"被系统丢掉，`cmd.exe` 在无控制台可继承的情况下自行分配一个新控制台。
   黑框标题就是命令行本身（`ping  -n 4 127.0.0.1`），活约 3 秒 —— 正好是 `ping -n 4` 的时长。
2. **静默失败**：命令以 **list 形式**传给 `subprocess`（`["cmd","/c",'… rd /s /q "D:/…"']`），
   `list2cmdline` 会把内层引号转义成 `\"`；而 **cmd.exe 不认反斜杠转义**（它用 `""` 表示字面引号）。
   `rd` 收到 `\"D:/…/"` 这种非法路径 → 报"文件名、目录名或卷标语法不正确"、退出码 **123**、
   **静默失败**。也就是说 **`_MEI` 解包目录从来没有被真正删掉过**，一直在往 `%TEMP%` 里堆。
   长期没被发现是因为子进程的退出码与输出都被丢进 DEVNULL：
   "看起来做了"和"真的做了"没有任何区别。

### 定位方式（都是实测，不是推断）
- 窗口：写探针枚举顶层窗口里的控制台窗口类（`ConsoleWindowClass` /
  `CASCADIA_HOSTING_WINDOW_CLASS` / `PseudoConsoleWindow`），spawn 前后取差集。
  **正控必须阳性**——故意用旧的 buggy 组合，若检不出窗口就直接判"探针失效"，
  因为看不见缺陷的探针给出的假通过比没有探针更危险（V-14 的教训）。
- 引号：三种写法各跑一次，看 `rd` 退出码与目录是否真的消失：

  | 写法 | cmd 退出码 | 目录已删 |
  | --- | --- | --- |
  | list 形式（修复前生产写法） | 123 | 否 |
  | 原始字符串 + `""path""`（现生产写法） | 0 | 是 |
  | 原始字符串 + `\"path\"`（对照） | 123 | 否 |

### 修复
- `_spawn_cleanup()`：只保留 `CREATE_NO_WINDOW`，补 `STARTUPINFO` 的 `SW_HIDE`。
- 改用**原始命令行字符串** + cmd 的 `""path""` 写法。
- 新增 `tools/check_no_console_window.py`：自带正反对照；`--exe` 覆盖
  `--cli` 出口与**图形界面投递 `WM_CLOSE` 关窗**出口（即用户实际报的那条路径），
  并核对 `%TEMP%` 下没有多出 `_MEI*` 残留。
- 代码结构：把 spawn 从 `_cleanup_frozen_exit` 抽出为可测的 `_spawn_cleanup(meipass, flags=…)`，
  `flags` 只为探针做对照用。

### 规格

- 新增 **NFR-08**（启动/运行/退出全过程不得产生计划外可见窗口；后台子进程一律
  `CREATE_NO_WINDOW`，且不得与 `DETACHED_PROCESS`/`CREATE_NEW_CONSOLE` 同用）、
  **NFR-09**（后台子进程不得静默失败，其**效果**必须有回归断言）、**FR-9.13**、**V-16**、
  待办 **G-09**（后台清理子进程运行期无失败痕迹）。

### 验证（干净环境，全部通过）
