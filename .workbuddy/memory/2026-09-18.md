## 修复 V-10：每点击一次格式卡片窗口就变宽

- 现象（用户报告）：【2. 输出设置】中每点一次文件类型图标，整个窗口变宽一点，可无限累积。
- 复现：实测 **+44px/次**，8 次累积 308px（对照实验 6 轮累积 440px）。
- 根因：`_autosize()` 用 `main.winfo_reqwidth() + 44` 反推窗口宽度。而 ttk.Treeview 的
  可伸缩列会随控件变宽而变宽，其请求宽度又按列宽计算 → 自增循环：
  `窗口变宽 → 拉伸列变宽 → reqwidth 变大 → 窗口再变宽`。
  格式卡片每次点击都经 `_sync_txt_fold() → _autosize()`，故每次点击放大一轮。
- 修复：新增 `gui.WIN_W = 988` 常量与 `Md2docsApp._window_width()`，窗口宽度取固定设计值，
  仅在工作区更窄时让步；彻底切断「内容宽度 → 窗口宽度」的反馈。
  实测内容自然宽度 944、设计宽度 988（与既有截图/验收值一致）。
- 验证：窗口宽度在点击格式卡片 / 开合折叠区共 43 次采样下恒为 988；四种折叠状态页脚均完整可见。

### 新增两个回归工具（防止复发）

- `tools/check_gui_width.py` —— 源码级：映射窗口 + 真实点击事件，断言宽度恒定。
  **必须映射**：`withdraw()` 下拉伸列不参与布局，缺陷不显现（已实测）。
- `tools/check_exe_gui.py` —— 产物级：对 `dist/Md2docs.exe` 投递真实鼠标点击，断言宽度恒定。
  实测 `PostMessage(WM_LBUTTONDOWN)` 对 Tk **无效**（顶层与最深子窗口都试过，高度无任何反应），

  用「点击 TXT 卡片高度必变」作为点击是否送达的证伪信号——否则"宽度恒定"是假通过。

## 缺陷 V-11：把文件拖进窗口 → 程序无提示直接退出（已修复）

### 现象与定位

用户报「把文件拖工具里，程序退出了」：**无异常、无弹窗、无日志，进程瞬间消失**。
拖到 EXE 图标上（命令行入口）不受影响。

定位手段：`tools/check_dnd.py` —— 按 shell 的 `HDROP` 内存布局（`DROPFILES` 结构 +
双 `\0` 结尾的 UTF-16 路径表）自行 `GlobalAlloc` 造句柄，再 `PostMessage(WM_DROPFILES)`。
这正是资源管理器拖放时发出的**同一条消息**，因此能真实复现且不依赖鼠标输入。

复现结果：
```
Fatal Python error: PyEval_RestoreThread: ... the current Python thread state is NULL
  File ".../tkinter/__init__.py", line 1481 in update
```

二分（四个变体）把范围压到单行：

| 变体 | 行为 | 结果 |
| --- | --- | --- |
| none | 不子类化窗口过程 | ✅ |
| trivial | 子类化，回调只 return | ✅ |
| noreaft | 回调里用 ctypes 解析出全部路径 | ✅ 路径正确 |
| full | 再追加一句 `root.after(0, …)` | 💥 进程死亡 |

### 根因

窗口过程是 **Tk 消息泵内部**被调用的，而 Tk 泵消息时在 C 层做了
`Py_BEGIN_ALLOW_THREADS`（**释放 GIL**）。此时回调里任何 Tcl/Tk 调用
（`root.after` / `event_generate` / 操作控件）都会破坏主线程状态 → 致命错误终止进程。
纯 ctypes 调用（`DragQueryFileW`/`DragFinish`）本身是安全的，**只有 Tcl 重入不安全**。

### 修复

窗口过程只做 `pending.append(int(wparam))` 然后立即 `return 0`；路径解析与界面更新
移到 Tk 定时器 `drain()`（`DROP_POLL_MS = 120ms`）里，在主线程正常上下文完成。
新增 `disable_file_drop(root)`，退出前还原原窗口过程并停表。确立硬约束 **UI-17**。
编号曾误写成 V-13，已统一为 **V-11**。

### 顺带修正的两件事

  旧证据必然失效会给出假结论。另新增 `top_level_at()` 校验目标点上是否是本窗口——

### 新增环境坑（重要）

- **本机 `env` 是自定义垫片**（`which env` → `~/.local/bin/env`）。
  `env -u PYTHONHOME -u PYTHONPATH <解释器> …` 会**静默吞掉整条命令**：返回 0、
  无输出、什么也不执行。本次一开始就被它误导，误以为"程序无输出/被硬杀"。
  正确做法是 bash 内建 `unset PYTHONHOME PYTHONPATH` 后再调用解释器。
- 桌面锁屏时，所有依赖真实鼠标/键盘输入的 GUI 测试都不可信。
  实测本机遮挡物是 **Windows 聚焦（Spotlight）全屏层**，类名 `Windows.UI.Core.CoreWindow`、
  标题「我们将切换到新图片。」、rect 覆盖 (0,0,1920,1080)；`WindowFromPoint` 在任意
  坐标都返回它。注意这**不是**标准锁屏（`LockScreenBackstopFrame` 那次才出现），
  所以只看类名容易误判成"没锁屏"。判定应以"目标点上是否真是目标窗口"为准。

### 为什么不用 Playwright / 鼠标模拟做拖拽验证（结论已固化）

- Playwright（含 agent-browser、playwright-cli）只能驱动**它自己启动的浏览器实例**，
  通过 CDP 在页面 DOM 上合成事件，**看不见也碰不到原生 Win32 窗口**。不是能力缺失，是射程问题。
- 本窗口用 `DragAcceptFiles` 注册的是 **Shell 拖放**：真实拖拽（Explorer 或 OLE
  `DoDragDrop`）最终都由 Shell 转成 `WM_DROPFILES` 投递到本窗口。因此投递该消息
  **与真实拖拽进入的是同一条消息、同一段窗口过程**；OLE 拖放源、鼠标捕获、Shell 解析
  全在 Md2docs 进程之外，不属于被测代码。这是"覆盖被测路径"与"覆盖外部通道"的区别。
- 因此把验证重心放在**handler 边界**而非外部通道，`tools/check_dnd.py` 已扩展为：
  单/多文件、重复去重、连续冲击 5 次、目录展开、不存在路径、非 Markdown 文件、
  大写扩展名、空 HDROP、非法 HDROP 句柄（0xDEADBEEF）、一次 150 个文件。
  源码模式 158 个文件全部收下且进程存活；EXE 与 `--argv` 入口均存活。
- **观察项（未改动行为，待用户决定）**：`_iter_md` 对**直接拖入的文件**不做扩展名过滤
  （只有目录展开时按 `MD_EXTS` 过滤），所以把 `pic.png` 直接拖进去会被加入列表。
  计数已按实际行为写断言。
