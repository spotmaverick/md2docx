## Md2docs 第三轮：用户三项反馈修复

### 1. 文件生成到 Documents\Md2docs 而非指定目录
- 根因：拖拽上传的 .md 落在 `Documents\Md2docs\上传的文件\`，前端默认"与源文件相同"→ 输出到上传目录（用户文档区被污染，用户以为没按指定目录）。
- 修复：
  - 上传缓存移到 `%TEMP%\Md2docs_uploads`（不再碰用户文档区）。
  - 前端默认输出模式改为"指定目录"，并预填 `Documents\Md2docs\转换结果`（config 返回 default_out）。
  - 选目录仍自动切 custom（上轮逻辑保留）。
- 验证：上传→输出到 default_out，位置精确。

### 2. 误报"已检测到 Word"（假装状态）——彻查结论
- 本机根本没有微软 Word（Uninstall 只有 WPS Office 商业版，磁盘无 winword.exe）。
- 真相：WPS 安装时**劫持了标准 Word.Application ProgID/CLSID {000209FF-...}**，把 LocalServer32 指向自己的 wps.exe。所以只看 ProgID 注册与否必然误报。
- 修复：com_helper 检测改为解析 CLSID → HKLM\SOFTWARE\Classes\CLSID\{id}\LocalServer32 的实际 exe，按归属分类：
  - winword.exe → word
  - 路径含 kingsoft/wps 或 wps.exe/et.exe/wpp.exe → wps
- 坑：pythoncom 没有 ProgID→CLSID 的 API（只有 ProgIDFromCLSID 反向），必须纯 winreg 读 HKCR\<ProgID>\CLSID。
- 结果：本机 word=False、wps=True。

### 3. 默认字体改微软雅黑
- theme.py: BODY_FONT / BODY_FONT_EA = "Microsoft YaHei"（原"等线"/"宋体"），MONO 保留 Consolas。
- rtf_writer.py 字体表 \f0 由 SimSun 改 Microsoft YaHei。
- 验证：docx 的 Normal/Heading 字体、RTF 字体表均为 Microsoft YaHei。

### 其他
- 打包前如 PermissionError，先 Get-Process Md2docs | Stop-Process -Force。
- 本机 WPS 为 32 位（WOW64 视图），读注册表要带 KEY_WOW64_32KEY。

## 第八轮（最终）：取消手动定位，改为拖入时自动定位源目录
- 用户要求取消手动"定位源文件"按钮，拖入 md 时自动定位源目录并显示到输出目录框。
- 自动定位实现（关键技巧）：浏览器不给拖放文件路径，但文件通常来自某个已打开的「文件资源管理器」窗口。
  - 新增 POST /api/locate {name}：遍历 Shell.Application().Windows()，过滤资源管理器窗口（_is_explorer：Name 含 Explorer/资源管理器，或 FullName 含 explorer.exe），把 LocationURL 用 _url_to_path 转成磁盘路径，检查该目录下 name 是否存在，命中即返回真实路径；未命中返回空。
  - COM 必须在 worker 线程里 pythoncom.CoInitialize/CoUninitialize，主线程 join(5s) 超时保护。
- 前端 initDrop：读 File.text() 后同步调 /api/locate；命中 → push {path}（等同浏览添加，same 模式显示源目录、按磁盘路径转换）；未命中 → 降级 {name, content, dropped}，显示"（拖入，未能自动定位源目录）"。
- 已删除：fi-locate 按钮、state.locateIndex、confirmBrowse 定位分支、弹窗标题分支。
- 验证：本机 6 个 Explorer 窗口全部正确枚举；README.md / CLAUDE.docx 精确定位到真实路径；不存在的文件与空名返回空；exe 冒烟正常，退出 rc=0。

## 第十轮：修复同名文件定位到旧目录的缺陷
- 缺陷：/api/locate 遍历所有 Explorer 窗口目录，先碰到哪个目录有同名文件就返回哪个。若旧目录（曾处理过）仍开着且也有同名文件，拖入新目录的同名文件会被定位到旧目录。
- 修复：新增"最近激活窗口优先"机制：
  - `_watch_active_explorer` 后台线程：每 1.5s GetForegroundWindow，若前台窗口类名 == "CabinetWClass"（资源管理器），枚举 Shell.Windows() 找 HWND 匹配的窗口，用 _url_to_path 记录其目录到全局 `_ACTIVE_EXPLORER_DIR`（list 单元素，跨线程安全）。
  - _locate 先查 _ACTIVE_EXPLORER_DIR 下是否存在该文件，命中即返回；未命中再遍历全部窗口兜底（保留旧行为）。
  - start_server 启动 watcher 线程。
- 原理：用户拖出文件前必然先激活过对应资源管理器窗口，故"最近激活目录"即最准确的源目录。
- 验证：watcher 捕获 os.startfile 激活的窗口正常；两目录同名 README.md 场景——激活 dist → 定位 dist；激活 .claude → 定位 .claude；exe 内同样验证通过，退出 rc=0。

## 第十三轮：图片统一「下载→嵌入」链路（docx/doc/wps）
- 需求：md 引用图片时，docx/doc/wps 等可嵌入格式要先下载图片并真正嵌入（不是写链接/占位），等比缩放不超版心宽，并居中。
- 现状核查：docx/RTF 本就在嵌入（WPS COM 实测 InlineShapes=7），但两处问题——docx 无 DPI 图片按 72dpi 假设计算导致小图放大 33%；超高图不受高度约束会超出页面。
- 实现：
  - 新增 src/imgsrc.py：统一解析网络 URL(含 // 协议相对)/data URI/file:// 本地路径，魔数嗅探格式(png/jpeg/gif/bmp/webp/svg) + 解析像素宽高，40MB 上限，带 UA/20s 超时。docx_writer 与 rtf_writer 的 load_image/load_bytes 旧实现删除。
  - docx 尺寸：96dpi 基准(1px=9525EMU)，scale=min(版心宽/自然宽, 版心高/自然高, 1)，小图自然尺寸、大图等比收缩进版心；块级图段落居中，行内图不整段居中。
  - RTF(doc/wps)：15twips/px(96dpi) 同基准，加 CONTENT_H(14004twips) 高度上限。
- 验证：WPS COM 打开 docx/doc/wps 三格式 InlineShapes 数量一致、尺寸一致（如 96px 图 72pt、宽图 453pt=16cm 版心宽、200x1600 超高图被限到高 699.8pt）；tools/check_output.py 增加图片断言（w:drawing→InlineShapes 非空且宽高≤版心；\pict 需带 png/jpeg blip、picwgoal/pichgoal≤CONTENT_W/H）；固件 tests/imgs_case.md + tests/assets/{wide,small,tall,mid}.png（另 1x1 data-URI、缺失图片降级占位不崩溃）。
- 经验：markdown 链接目标里反斜杠路径/回车容易踩坑；验证"渲染器是否真嵌入"最可靠是 WPS COM 数 InlineShapes，比解包 XML 更接近用户视角。venv 为 envs/md2docs，调用必须 env -u PYTHONHOME -u PYTHONPATH。
